# 示例：用户实际会怎样使用这个系统

## 例 1：首次四关

用户对普通 ChatGPT 说：

> 帮我验证当前 Mac MCP 是否真的能读取和修改我的 Mac。只在新建的临时测试目录里做 A 工具发现、B 读取、C 写文件并读回、D 修改并二次读回。每一步只按照真实工具结果标记 PASS，不要改变其他文件或权限。

预期：有工具的 Chat 产生真实回执；无工具的 Chat 清楚说明原因。**没有真实回执不算通过。**

## 例 2：日常开发

用户：

> 修复当前仓库的配置解析错误。你是主控，先验证我的 Git 状态，然后用已连接的 Mac MCP 派一个 Codex 执行器在隔离工作树里查错、改代码和补测试。你独立审查后才合并并提交。小问题自己解决，额外付费或越权才问我。

主控：先只读检查 Mac MCP、Git、模型 catalog、授权目录；给 Codex 任务描述；真实等结果；测试；保存 checkpoint。

## 例 3：Codex 遇到问题

Codex：

```text
NEEDS_CONTROLLER:
现有库会读取旧版本 JSON。
方案 A 保持兼容并新增旧版测试；方案 B 完全迁移。
建议 A，风险较小。
```

主控判断：把 A 直接通过官方 `agent_action(message)` 交回**同一个有效 Codex 原生会话**。如果工具/会话不支持，标失败或安全接力新 Codex，**不让用户去打开一条云 Work 帮忙传话**。

## 例 4：Codex 自称完成，但主控验收失败

Codex：

```text
RESULT: 已修复；本隔离工作树 12 个单测 PASS。
WARNING: 隔离沙箱不可读取父 Git 元数据，未跑 git diff --check。
```

主控：不能直接写全 PASS。先读隔离改动、确认范围，必要时通过受控 apply 合并到源仓库，并在源仓库重跑 Git 与测试；失败则返工，成功再提交。**这才是“不是笨模型帮你做所有决策”。**

## 例 5：旧 session 无法继续

Mac MCP 返回：

```text
thread/resume failed: no rollout found
```

主控：记录真实报错，停止盲目重复，检查是否有未知副作用，从最后可信 Git HEAD/本地任务状态接力新的 Codex 原生 session。**不要称为原 Work 聊天已被唤醒。**
